## 0. Архитектурные решения (зафиксировано)

| Вопрос | Решение |
| --- | --- |
| Откуда цифры | `window.__HOT_COINS_SNAPSHOT__` — график сам отдаёт то, что реально нарисовал (правка в репо `inp`). Не парсим DOM, не кликаем кнопку настроек, не ходим в CoinGecko |
| Текст | v1 — шаблоны с ветвлениями (без LLM). ИИ добавляется в v2 заменой одной функции |
| Конечный хостинг | контейнер на том же VPS, где inp.one, запуск по cron (обоснование — раздел 7) |
| Язык | TypeScript + Playwright (снапшот-контракт шарится типами с сайтом) |
| Отладка | сначала локально через `DRY_RUN=1`, потом деплой (раздел 6) |

## 1. Формат поста (эталон)

```jsx
<b>🌅 Утро на рынке — 14 июля</b>

<b>🔴 BTC $62,559 (−0.59%)</b>

Второй день подряд рой красный: биток медленно сползает, большинство монет в минусе — 38 падают против 17 растущих в основном рое.

<b>📈 Против течения: DRV +25%</b>
📉 Антигерой дня: CX −25%

Интересно, что рынок падает без паники: биток теряет доли процента, а альты по краям роя штормит на ±25%. Классическая картина «тихого» слива — деньги не уходят с рынка, а перебегают между монетами.

Вся карта в реальном времени → inp.one
```

Структура жёсткая, меняется только контент:

1. Заголовок: `🌅 Утро на рынке — {дата по-русски, без года}` (`14 июля`, без ведущего нуля). **Жирная** — оборачивается в `<b>…</b>`.
2. Строка BTC: `{🔴|🟢} BTC ${цена} ({±X.XX%})`. Эмодзи по знаку 24h. Цена — разделитель тысяч запятой, без копеек если ≥ $1000. Минус — типографский `−` (U+2212), не дефис. **Жирная** — оборачивается в `<b>…</b>`.
3. Абзац-картина дня — из шаблонов (раздел 4).
4. Строки лидеров — из шаблонов (раздел 4). **Строка роста всегда первая, строка падения второй.** По одной монете в каждой строке (второго лидера в v1 нет). Строка роста — **жирная** (`<b>…</b>`), строка падения — обычным текстом.
5. Абзац-наблюдение — из шаблонов (раздел 4). Никогда не прогнозы и не советы.
6. CTA: `Вся карта в реальном времени → inp.one`.
7. Вложение: PNG графика. Пост = `sendPhoto` с caption (лимит 1024 символа).

## 2. Шаг 1 (сайт): снапшот в `window`

Правка в репо `OnixFireOne/inp`, компонент `components/HotCoinsBeeswarm.tsx`. После того как рой отрисован — положить в `window` ровно то, что пошло в канвас:

```tsx
export type HotCoinsSnapshot = {
	version: 1
	ts: string                 // ISO, момент рендера
	btc: { price: number; change24h: number } | null
	mainSwarm: SwarmCoin[]     // то, что в основном рое
	edgePins: SwarmCoin[]      // прижатые к краям
}
export type SwarmCoin = {
	id: string                 // coingecko id
	ticker: string             // ВЕРСАЛЬНОЕ, как на графике
	change24h: number          // проценты, не доли
	price: number
	marketCap: number | null
}
```

Требования к этой правке:

- Пишется **только после фактического рендера** и из того же массива, который рисует ноды, после всех фильтров и разделения на рой/края. Никакого второго источника данных — иначе текст разойдётся с картинкой.
- **Запись включается только по query-параметру** `?snapshot=1`. Обычный посетитель inp.one никакого снапшота не получает — ему этот объект ни для чего не нужен. Проверка флага делается один раз при монтировании (`useSearchParams` или `location.search`), результат — в `useRef`.
- Флаг не должен **никак** влиять на рендер: те же монеты, те же фильтры, та же раскладка. Иначе скрипт будет видеть не то, что видят люди.
- Запись идёт **только когда меняются сами данные** (состав монет или их цифры), а не на каждый кадр анимации и не на каждый ререндер. Нормально, если за загрузку запись сработает несколько раз — страницы данных приходят по 100 монет (см. раздел 3, скрипт ждёт стабилизации).
- Никакого `console.log` со снапшотом в проде. Лог типа `[hot-coins-snapshot] {…}` удобен для отладки, но на боевом сайте это сотни килобайт в консоль на каждой загрузке — либо убрать, либо только под `?snapshot=1`.
- Никакого влияния на UI, разметку и производительность. Селектор `id="hot-coins-chart"` сохранить — от него зависит и news-radar.
- Тип `HotCoinsSnapshot` вынести в отдельный файл (`lib/hotCoinsSnapshot.ts`). Этот файл — **единственный источник контракта**. Поле `version` — чтобы скрипт мог ругаться при смене контракта, а не молча падать.
- Копирование этого типа в `src/types.ts` репо morning-post — не часть работы по `inp`, это делает шаг 2 плана (раздел 9) вместе с каркасом. В `inp` ничего про morning-post знать не нужно; репо не связаны зависимостью, только общим `version`.
- Запись живёт в `draw()` — это правильное место (тот же `s.nodes`, тот же `isOffScreen()`), но `draw()` — кадровый цикл. Обязательно гасить частоту: сравнивать дешёвый ключ и пересобирать объект только при его изменении, или не чаще раза в ≈две секунды.
- Ключ троттлинга = ссылка на массив данных + число нарисованных нод + **число краевых пинов**. Третье слагаемое обязательно: разделение на `mainSwarm` и `edgePins` считается по `isOffScreen()` каждый кадр, и монета может перейти через порог при том же составе и том же числе нод. Без него в снапшоте останется устаревшее разделение — то есть текст о «краях роя» разойдётся с картинкой. Подсчёт пинов почти бесплатен: `isOffScreen()` всё равно прогоняется каждый кадр в `drawEdgePins()`.
- Поверх ключа — **пол по времени**: не пересобирать снапшот чаще раза в ≈500 мс, даже если ключ меняется чаще. При pan/zoom монеты пересекают границу почти каждый кадр, и без пола троттлинг перестаёт работать ровно в тот момент, когда он нужен. Скрипту это безразлично: он не крутит график и ждёт стабилизации.
- Отложенная полом запись не должна теряться. Проверено по коду (21.08): rAF-цикл компонента **безусловный** — `requestAnimationFrame(loop)` перепланируется в конце каждого вызова, без условия выхода; останавливает его только `cancelAnimationFrame` в cleanup при анмаунте. Значит отложенная запись всегда получит следующий кадр — в том числе в фоновой вкладке (браузер душит rAF до ≈одного кадра в секунду, но не останавливает). Отдельный `setTimeout`-flush не нужен.
- **Если в будущем цикл сделают останавливающимся** при успокоении роя (типичная оптимизация батареи) — flush становится обязательным. Иначе последнее изменение, попавшее под пол, останется незаписанным, и скрипт молча возьмёт устаревшее разделение `mainSwarm`/`edgePins`.
- В снапшот кладутся **плоские копии** пяти полей `SwarmCoin`, а не ссылки на живые ноды симуляции (иначе внутрь попадёт анимационное состояние, а сериализация в `page.evaluate()` может упасть на циклических ссылках).
- Приёмка правки (проверять на живом сайте после деплоя):
    - На `inp.one/?snapshot=1` — `window.__HOT_COINS_SNAPSHOT__.mainSwarm.length` равно числу видимых нод в рое, `edgePins.length` — числу краевых пинов.
    - На `inp.one` без флага — `window.__HOT_COINS_SNAPSHOT__` равен `undefined`, в консоли чисто.
    - Перетаскивание косметических ползунков не плодит записей; смена режима/topN и догрузка страницы — плодят ровно по одной.

## 3. Шаг 2 (скрипт): забор данных и скриншот

Один запуск Chromium, один заход на сайт, из него и данные, и картинка:

```tsx
const browser = await chromium.launch()
const page = await browser.newPage({ viewport: { width: 1200, height: 900 }, deviceScaleFactor: 2 })
// domcontentloaded, НЕ networkidle: на dev-сервере Next.js висит HMR-соединение
// и networkidle может не наступить никогда. Готовность ловим снапшотом ниже.
await page.goto(SITE_URL, { waitUntil: "domcontentloaded", timeout: 60_000 })

// Данные приходят страницами по 100 монет, снапшот перепишется 2–3 раза.
// Ждём не «появился», а «перестал расти» — иначе пост уйдёт по первой сотне.
await page.waitForFunction(
	(min) => (window.__HOT_COINS_SNAPSHOT__?.mainSwarm?.length ?? 0) >= min,
	MIN_SWARM_SIZE,
	{ timeout: 45_000 },
)

let prev = -1
for (let i = 0; i < 20; i++) {
	const size = await page.evaluate(() => {
		const s = window.__HOT_COINS_SNAPSHOT__
		return s.mainSwarm.length + s.edgePins.length
	})
	if (size === prev) break // два одинаковых чтения подряд — данные устоялись
	prev = size
	await page.waitForTimeout(1500)
}
await page.waitForTimeout(1200) // доиграть анимацию раскладки роя

const snapshot = await page.evaluate(() => window.__HOT_COINS_SNAPSHOT__)
const png = await page.locator("#hot-coins-chart").screenshot({ type: "png" })
```

- Скринится **строго контейнер графика**, не весь экран. `deviceScaleFactor: 2` — чтобы текст на графике был резким в Telegram.
- Если сайт темно-светлый по теме — принудительно тёмная: `colorScheme: "dark"` в `newPage`, чтобы посты были однообразными.
- Скрыть мешающее перед скриншотом (если лезет в кадр): куки-баннер, тултипы, ховер-состояния — впрыском CSS через `page.addStyleTag`. Курсор увести за пределы графика (`page.mouse.move(0, 0)`), иначе может всплыть тултип монеты.
- **Кликать кнопку настроек НЕ нужно.** Топы/лузеры считаются из снапшота сортировкой, а не вытаскиваются из скрытой панели UI.
- Заходить обязательно на URL с флагом `?snapshot=1` — без него сайт снапшот не пишет вообще (раздел 2). Флаг зашит в `SITE_URL`. Если `waitForFunction` выпал в таймаут — первое, что проверять в алерте: был ли флаг в URL.
- Котировка BTC — из `snapshot.btc`. Если биток по какой-то причине не попадает в рой, отдавать его в снапшоте отдельным полем из тех же рыночных данных страницы (не ходить в CoinGecko из скрипта).

## 4. Шаг 3: факты и текст без ИИ

### 4.1 Счёт фактов (чистая функция `computeFacts(snapshot, history)`)

```tsx
type Facts = {
	dateLabel: string          // "14 июля"
	btc: { price: number; change24h: number }
	red: number; green: number; total: number
	swarmState: "red" | "green" | "mixed"
	streak: number             // сколько дней подряд то же состояние
	losers: SwarmCoin[]        // отсортировано по change24h asc
	winners: SwarmCoin[]       // desc
	maxAbsEdgeChange: number
}
```

Правила:

- `dateLabel` и ключ дня для `state.json` считаются **явно через** `Intl.DateTimeFormat("ru-RU", { timeZone: "Europe/Moscow", … })`, а не через локальную дату машины и не через `process.env.TZ`. На Windows `TZ` работает ненадёжно, а таймзона разработчика (Asia/Almaty) на 3 часа впереди Москвы: без явной таймзоны локальные тесты будут давать другую дату, чем прод, и сломаются идемпотентность и стрик. Покрыть тестом на границе суток (23:30 МСК).
- `red` / `green` — только по `mainSwarm`. Нулевые (±0.05%) не считать ни туда, ни туда; `total = red + green`.
- Лидеры — по `[...mainSwarm, ...edgePins]` (края важны: там самые сочные цифры). Исключить стейблы и фонды денежного рынка по списку тикеров (USDT, USDC, DAI, USDE, FDUSD, **USDGO**, **EURSAFO**…) — список в константе, легко расширяем. Дополнительно отбрасывать всё, у чего `change24h == 0` и цена близка к 1 — страховка от новых стейблов, которых нет в списке.
- `swarmState`: `red` если `red / total >= 0.6`, `green` если `green / total >= 0.6`, иначе `mixed`.
- `streak` — сравнением с `state.json` (см. 5). Первый запуск → `streak = 1`. Дыра в истории (пропущенный день) обрывает стрик — не врать «третий день подряд», если данных за вчера нет.
- Функция чистая и покрыта юнит-тестами (vitest) на фикстурах — без браузера и сети.

### 4.2 Сборка текста (`buildParagraphs(facts)`)

Словарь фраз в отдельном файле `phrases.ts` — чтобы править тексты не трогая логику. На каждую ветку — **минимум 3 варианта** формулировки, выбор детерминированный по дате (`dayOfYear % variants.length`) — воспроизводимо в тестах и не повторяется два дня подряд.

**Абзац 1 — картина дня**, ветки:

| Условие | Пример фразы |
| --- | --- |
| `red` && `streak >= 2` | «{Второй|Третий|Четвёртый…} день подряд рой красный: биток медленно сползает, большинство монет в минусе — {red} падают против {green} растущих в основном рое.» |
| `red` && `streak == 1` | «Рой развернулся в минус: {red} монет падают против {green} растущих.» |
| `green` && `streak >= 2` | «{N}-й день рой держится в зелёном: {green} монет в плюсе против {red} падающих.» |
| `green` && `streak == 1` | «Рой зеленеет после падения: {green} монет в плюсе против {red} в минусе.» |
| `mixed` | «Рынок разошёлся: {green} монет в плюсе, {red} в минусе — единого направления нет.» |

**Строки лидеров:**

- Порядок строк **всегда один и тот же**: сначала рост, потом падение. По одной монете в каждой строке — `winners[0]` и `losers[0]`. Второй лидер («следом …») в v1 не выводится (задел на будущее: включить при `|L2| >= 10%`).
- Строка роста — жирная: `<b>📈 {подпись}: {W1.ticker} {+X%}</b>`. Строка падения — обычная: `📉 {подпись}: {L1.ticker} {−X%}`.
- Подписи зависят от состояния роя: при `green` — «Герой дня» для роста и «Против течения» для падения; при `red` и `mixed` — «Против течения» для роста и «Антигерой дня» для падения.
- Проценты: округлять до целого при `|x| >= 10`, до одного знака при `< 10`. Как в эталоне: `−25%`, `−15.5%`.

**Абзац 2 — наблюдение**, ветки по характеру движения:

- `|btc%| < 1 && maxAbsEdgeChange > 15` → «тихий слив / деньги перебегают между монетами» (фраза из эталона).
- `|btc%| >= 3` → «движение ведёт биток: его {±X%} тянет за собой весь рой».
- `maxAbsEdgeChange < 8` → «Спокойный день: даже на краях роя никто не вышел за ±{X}%».
- иначе — нейтральная ветка про контраст BTC и альтов.

Жёсткие запреты для всех фраз: без прогнозов, без советов «покупать/продавать», без обещаний иксов, без хэштегов. Все числа и тикеры — только подстановками из `Facts`, никаких зашитых в текст цифр.

### 4.3 Сборка caption

- Склеить блоки из раздела 1, проверить длину ≤ 1024 (с учётом HTML-тегов). Если не влезает — сначала убирается абзац-наблюдение, затем берётся короткий вариант абзаца-картины. Заголовок, строка BTC, строки лидеров и CTA не режутся никогда. Порядок деградации зафиксировать в коде, не резать строку посередине.
- Отправлять с `parse_mode: "HTML"` — нужен для жирных строк. Жирным оборачиваются ровно три строки: заголовок, строка BTC, строка роста.
- Раз включён HTML — **экранировать `&`, `<`, `>` во всех подставляемых значениях** (тикеры приходят с сайта, там может оказаться что угодно). Экранирование делается до оборачивания в `<b>`, отдельной функцией `escapeHtml()`, покрытой тестом.
- Разрешённые теги — только `<b>`. Никаких `<a href>`: ссылка `inp.one` в CTA становится кликабельной автолинком сама.
- Лимит 1024 считается по видимому тексту, но Telegram считает вместе с тегами — проверять длину итоговой HTML-строки.

## 5. Шаг 4: состояние и публикация

`state.json` (плоский файл, никакой БД):

```json
{
  "days": [
    { "date": "2026-07-13", "swarmState": "red", "btcChange": -0.4, "postedAt": "2026-07-13T04:00:11Z", "messageId": 812 }
  ]
}
```

- Хранить последние ~60 дней, старое обрезать. Запись — атомарная (в tmp-файл + `rename`), чтобы падение не било историю.
- **Идемпотентность**: если за сегодняшнюю дату (в `TZ` поста) уже есть `postedAt` — выйти без публикации с кодом 0 и логом. Защита от двойного крона и ручного ретрая. Флаг `--force` для ручного перепоста.
- Публикация — Telegram Bot API `sendPhoto` (multipart, PNG из памяти, без записи на диск), `chat_id = TELEGRAM_TARGET_CHAT_ID`, `parse_mode: "HTML"`. Сохранить `message_id` в state.
- Целевой чат меняется **только через env**: на старте там личный chat_id владельца, после обкатки — id канала. Никаких правок кода при переключении, никаких списков получателей.

## 6. Как это запускается: локально и на сервере

Это **одноразовый скрипт**, не сервер: запустился → сделал пост → завершился с кодом 0. Никакого демона и внутреннего планировщика — расписание снаружи (cron).

### Локальная отладка (сначала только это)

```bash
npm i && npx playwright install chromium
cp .env.example .env      # Windows: copy .env.example .env
npm run dry               # собирает пост, не публикует
```

**Среда разработки — Windows, прод — Linux-контейнер.** Отсюда жёсткие требования:

- **Никаких переменных префиксом в командах**: `DRY_RUN=1 npm start` в PowerShell и cmd не работает. Все настройки читаются из `.env` через `dotenv`, а режимы живут отдельными npm-скриптами (`dry`, `dry:fixture`, `post`, `post:force`) с `cross-env` внутри.
- Пути — только через `path.join` / `path.resolve`, без зашитых слешей. `./out` и `./data` создавать кодом (`mkdirSync(..., { recursive: true })`), а не руками и не `mkdir -p` в скрипте.
- `.gitattributes` с `* text=auto eol=lf` — иначе CRLF из Windows попадёт в `Dockerfile` и shell-скрипты и сломает сборку на сервере с неочевидной ошибкой.
- Никаких баш-однострочников в npm-скриптах (`&&` допустим, `rm -rf`, `cp`, `export` — нет). Чистка папок — средствами Node.
- Node 24 в разработке и в контейнере — одной мажорной версии. Зафиксировать в `package.json` через `"engines": { "node": ">=24 <25" }`.

`DRY_RUN=1` обязан: печатать готовый caption в stdout, класть PNG в `./out/YYYY-MM-DD.png`, рядом складывать `./out/YYYY-MM-DD.facts.json` (сырые факты) — чтобы глазами сверить цифры с картинкой. Не трогать `state.json` в dry-run.

Дополнительно для отладки: `SNAPSHOT_FILE=./fixtures/day.json npm start` — взять снапшот из файла вместо браузера. Позволяет прогнать все ветки текста (зелёный день, mixed, скучный день) не ждая такой погоды на рынке.

### Полный прогон против локального сайта (до мержа в `inp`)

Правка со снапшотом живёт в ветке `inp` и в прод не выложена — значит весь пайплайн (снапшот → скриншот → текст → отправка) прогоняется против локально поднятого `inp`. `SITE_URL=http://localhost:3000/?snapshot=1` — больше ничего в скрипте менять не надо.

- Гонять локальный сайт в режиме прод-сборки (`next build && next start`), а не `next dev`. Dev-режим — другие тайминги рендера и другая картинка (dev-индикаторы, несжатые бандлы). На `next dev` тестится логика, но не финальный вид поста.
- `waitUntil: "networkidle"` не использовать вообще (см. раздел 3): на dev-сервере HMR держит соединение открытым, и шаг повиснет до таймаута.
- Повторные прогоны в один день блокирует идемпотентность — для тестов запускать с `--force` либо держать отдельный `STATE_FILE=./data/state.test.json`.
- Реальная отправка в Telegram на этом этапе безопасна: `TELEGRAM_TARGET_CHAT_ID` всё равно указывает в личку владельца, а не в канал.
- Порядок выхода в прод: зелёный e2e на локали → мерж PR в `inp` → деплой сайта → проверка приёмки снапшота на живом `inp.one/?snapshot=1` → смена `SITE_URL` на продовый → cron.

### Продакшн: контейнер на VPS + cron

- `Dockerfile` на базе `mcr.microsoft.com/playwright:v1.XX-jammy` (браузер и системные библиотеки уже внутри — не собирать зависимости вручную).
- **Версия образа обязана совпадать с версией пакета** `playwright` в `package.json` (та же `1.XX`). Расхождение даёт «browser not found» или тихо другой рендер скриншота, чем на лолали. При обновлении Playwright править оба места одним коммитом.
- Версии всех зависимостей в `package.json` — точные, без `^` и `~`. `package-lock.json` коммитится, в контейнере ставится `npm ci`, а не `npm i` — иначе сборка через месяц подтянет другие версии, чем проверенные локально.
- Свой `compose.yml`: один one-shot сервис `morning-post` с `restart: "no"`, volume для `state.json`, env из `.env`.
- Системный cron на хосте с явной таймзоной, чтобы не зависеть от таймзоны сервера:

```jsx
CRON_TZ=Europe/Moscow
0 9 * * * cd /opt/morning-post && docker compose run --rm morning-post >> /var/log/morning-post.log 2>&1
```

- 09:00 МСК = 12:00 Asia/Almaty. Если `CRON_TZ` не поддерживается кроном на хосте — ставить `0 12 * * *` и всё равно передавать `TZ=Europe/Moscow` в контейнер (от этого зависит дата в заголовке и ключ дня в `state.json`). Переход на летнее время в РФ отсутствует, пересчёт не нужен.
- Деплой — тем же способом, что сайт (GHCR + `docker compose pull`), чтобы не заводить второй процесс выкладки.

### Почему VPS, а не GitHub Actions

GitHub Actions тоже работает и не требует сервера, но для ежедневного поста его минусы реальные:

|  | VPS + cron (выбрано) | GitHub Actions cron |
| --- | --- | --- |
| Точность времени | минута в минуту | опоздания до 10–30 мин в часы пика, иногда пропуск запуска |
| Состояние (`state.json`) | volume, тривиально | либо коммит в репо каждый день, либо cache, который может быть вытеснен → сломанный стрик |
| Старт запуска | образ уже на диске, секунды | 1–2 мин на установку зависимостей и браузера каждый раз |
| Сеть до inp.one | локально, быстро и без CDN-сюрпризов | из датацентра GitHub, возможен rate-limit/geo-кэш |
| Секреты | `.env` рядом с сайтом | repo secrets (тоже нормально) |

Итог: сервер у тебя уже есть и сайт на нём же — платить за «без сервера» шатким расписанием и хранением истории в гите смысла нет. Но Actions-воркфлоу всё равно сделать — только с `workflow_dispatch` (ручной тестовый запуск в dry-run из веб-интерфейса), без `schedule`.

## 7. Структура репозитория

Отдельный репо `OnixFireOne/morning-post`:

```jsx
src/
  index.ts          // оркестрация: шаги 1→5, обработка ошибок, коды выхода
  capture.ts        // Playwright: снапшот + PNG
  facts.ts          // computeFacts() — чистая
  phrases.ts        // словарь фраз по веткам
  render.ts         // buildParagraphs() + caption, чистая
  telegram.ts       // sendPhoto / sendMessage / алерт админу
  state.ts          // чтение/атомарная запись state.json, стрик
  types.ts          // HotCoinsSnapshot (копия контракта с сайта)
fixtures/           // снапшоты для тестов: red/green/mixed/boring/edge-cases
tests/              // vitest: facts.test.ts, render.test.ts, state.test.ts
Dockerfile
compose.yml
.env.example
.gitattributes      // * text=auto eol=lf — иначе CRLF из Windows сломает сборку в Linux
.gitignore          // .env, /out, /data, node_modules
README.md           // как запустить локально (вкл. Windows), как выложить, как править фразы
```

Правило разделения: вся логика фактов и текста — чистые функции без сети и браузера; всё грязное (Playwright, Telegram, файлы) изолировано в своих модулях. Иначе тесты потребуют браузер и будут флаковать.

### env (`.env.example`)

```jsx

CHART_SELECTOR=#hot-coins-chart

```

## 8. Устойчивость и ошибки

- Сайт не открылся / снапшот пустой / монет меньше `MIN_SWARM_SIZE` → 2 ретрая с паузой 30 с (новый контекст браузера). После — алерт админу, выход с кодом 1, без поста (лучше пропустить день, чем опубликовать враньё).
- Снапшот есть, а скриншот не вышел → постить текстом без фото (`sendMessage`) + алерт. Цифры важнее картинки.
- `snapshot.version != 1` → внятная ошибка «контракт снапшота изменился» + алерт, без поста.
- Telegram ответил 429/5xx → 3 ретрая с экспонентой, уважать `retry_after`.
- Любое падение — структурный лог в stdout + сообщение админу с причиной. Никаких молчаливых пропусков дня.
- Не логать токен бота ни при каких ошибках.

## Канал, бот, время (зафиксировано)

- **Бот** — тот же, что у news-radar. Отдельного бота не создавать, токен переиспользуется.
- **Канал** — тот же, что дайджест news-radar. Но на старте пост уходит **в личку владельцу** (`TELEGRAM_TARGET_CHAT_ID` = личный chat_id), в канал переключается позже сменой одной переменной окружения.
- **Ошибки, алерты, предупреждения** — всегда в личку владельцу (`TELEGRAM_ADMIN_CHAT_ID`), независимо от того, куда идёт сам пост. В канал ошибки не попадают никогда.
- **Время** — ежедневно в 09:00 по Москве. Таймзона расписания и таймзона даты в заголовке — одна и та же (`Europe/Moscow`).
